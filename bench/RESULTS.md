# 压测报告:简历提交接口(异步化验证)

> 日期:2026-09-13 / 环境:应用本机运行(mvn spring-boot:run,默认 application.yml),
> 中间件(PostgreSQL / Redis / RustFS)部署于远程服务器 <remote-host>,
> 本机与服务器之间的网络往返(RTT)实测约 **600~800ms**。

## 一、实测数据

### 1. 环境基线(单次 REST 往返,GET /api/auth/me,含 JWT 验签 + 1 次 DB 查询)

| 样本 | 耗时 |
|---|---|
| 1 | 804 ms |
| 2 | 1259 ms |
| 3 | 814 ms |

→ 每一次"本地应用 ↔ 远程中间件"的往返成本约 0.6~0.8s(对象存储健康探测同理,617~645ms/次)。

### 2. 提交接口(POST /api/resumes/upload,内容去重命中路径)

| 指标 | 实测 |
|---|---|
| 首次(含连接预热) | 5538 ms |
| 后续样本(2~6) | 2938~3486 ms |

### 3. 结论与归因

- 提交接口耗时 ≈ 基线 RTT × 请求路径上的中间件交互次数。
  在"应用与中间件分离"的部署下,**网络往返主导了提交耗时**,业务逻辑本身
  (Tika 解析、JSON 序列化、XADD 入队)为毫秒级 CPU 操作。
- 异步化的核心价值与部署形态无关:**把"同步等待 AI 分析(十几秒)"从请求路径中移除**,
  提交耗时变成一个与 AI 耗时无关的固定小开销,且任务落库可重试、可观测。
  优化前同步口径的量级由"任务端到端耗时"实测给出(见下节方法)。

### 4. 当次环境的一个插曲(可作为面试素材)

压测过程中远程 Redis 出现 `Unable to init enough connections amount! Only 3 of 10`,
PostgreSQL 出现 SSL 握手阶段 EOF——中间件连接池被网络质量拖垮,应用启动失败 3 次。
排查路径:先区分"应用问题"还是"环境问题"(换基线接口对比 → 直连中间件端口探测),
最终定位为远程链路不稳定,而非代码缺陷。

## 二、复现方法(中间件可用时执行)

```bash
# 1. 启动应用(本地部署方式)
mvn -pl app spring-boot:run

# 2. 注册账号后执行(20 份内容各异的样本简历已就绪,绕开内容哈希去重、走完整提交路径)
bash bench/run-bench.sh http://localhost:8080 <用户名> <密码> bench/resumes 20
```

脚本输出三组数字:
1. **基线 P50**:单次 REST 往返(用于把网络成本从业务耗时里剥出来);
2. **提交延迟 P50/P95**:异步化后口径,理想环境(中间件同机/同内网)即简历中
   "200ms 量级"的对应值;
3. **任务端到端耗时**(抽样 3 条,上传到 COMPLETED):即旧同步接口"等 AI 分析"的
   量级(十几秒),与提交延迟的对比就是本次优化的完整故事。

## 三、面试口径建议

- 数字要与环境绑定表述:"在中间件与应用同机的环境下,提交接口 P95 为百毫秒级;
  在我当前的分离部署下实测为 X 秒,其中基线往返就占 Y 秒——但无论哪种部署,
  提交耗时都不再依赖 AI 分析时长,这才是异步化的意义。"
- 或者把简历措辞改为不受环境影响的说法:
  "将同步等待 AI 分析(秒级)重构为 Redis Stream 异步任务,提交接口响应与 AI 耗时解耦"。
- 若想拿到干净的 200ms 实测:把 PostgreSQL/Redis/MinIO 与应用跑在同一台机器
  (本机 docker compose 或同内网 VPS),重跑上面脚本即可。
