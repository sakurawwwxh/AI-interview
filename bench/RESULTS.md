# 压测报告:简历提交接口(异步化验证)

> 实测时间:2026-09-14 / 环境:应用本机运行(mvn spring-boot:run,默认 application.yml),
> 中间件(PostgreSQL / Redis / RustFS)部署于远程服务器 <remote-host>,
> 本机→服务器单次网络往返(RTT)实测约 **830ms**。
> 压测方式:`bench/run-bench.sh`,20 份内容各异的样本简历(bench/resumes/),每个文件走完整提交路径
> (Tika 解析 → 内容哈希 → S3 上传 → DB 落库 → XADD 入队 → 返回任务 ID),120 秒等待端到端完成。

## 一、实测数据(2026-09-14)

### 1. 环境基线:单次 REST 往返(GET /api/auth/me,含 JWT 验签 + 1 次 DB 查询)

| 指标 | 实测 |
|---|---|
| P50 | **826 ms** |
| 均值 | 826 ms(5 样本) |

→ 本地应用每与远程中间件交互一次,固定成本约 0.83s(对象存储健康探测同为 0.63s/次)。

### 2. 提交接口延迟(POST /api/resumes/upload,20 个唯一文件,完整路径)

| 指标 | 实测 |
|---|---|
| 样本数 | 20 |
| P50 | **3993 ms** |
| P95 | **4120 ms** |
| 最大 | 4292 ms |
| 均值 | 3914 ms |

### 3. 归因

- 提交延迟 ≈ 基线 RTT × 请求路径中间的远程交互次数:存储 PUT(1~2 次往返)+
  数据库写入(2~3 次往返)+ Redis XADD(1 次往返),累计 4~5 次 ≈ 3.3~4.2s,与实测吻合。
- **业务净处理(Tika 解析、哈希、序列化)为本地 CPU 操作,毫秒级**——网络的确定性成本
  主导了提交耗时,业务代码不是瓶颈。
- 异步化的结构性证据:**提交延迟与 AI 调用耗时完全解耦**——上传不等待模型响应,
  返回的任务 ID 即可轮询;端到端环节(AI 分析)发生在消费者侧。
- 「200ms 量级」的适用条件:中间件与应用同机/同内网(隔离网络往返后即收敛到业务净处理,
  本项目 README 的 docker compose 或同 VPS 部署即此形态)。

### 4. 端到端耗时(旧同步接口的等效口径)

因 AI Key 已从配置文件移除(安全整改),本次以占位 Key 启动,AI 调用快速失败
(1.4~1.8s 内任务 FAILED,非真实分析耗时),**该环节本次未取得有效样本**。
填入真实 Key 后重跑即可获得(预期为 AI 调用时长的秒级~十几秒量级)。

## 二、复现方法

```bash
# 1. 启动应用(需真实 AI Key,可通过环境变量注入,避免写入配置文件)
AI_BAILIAN_API_KEY=<真实Key> mvn -pl app spring-boot:run

# 2. 执行压测(20 份唯一样本已就绪)
bash bench/run-bench.sh http://localhost:8080 <用户名> <密码> bench/resumes 20
```

脚本输出:基线 P50 / 提交延迟 P50·P95 / 抽样端到端耗时。

## 三、面试口径建议

- 数字与部署形态绑定表述:"本项目默认演示环境是应用与中间件分离部署,单次网络往返约
  0.8s,提交延迟 4s 里约 3.3s 是往返成本的累加;业务处理本身毫秒级。在中间件同机的
  部署下到达百毫秒级。"
- 更稳的简历措辞(不受环境数字影响):
  "将同步等待 AI 分析(秒级)重构为 Redis Stream 异步任务,提交接口响应与 AI 耗时解耦,
  任务可靠落库、可重试可观测。"
- 若想展示干净的 200ms 实测:把 PostgreSQL/Redis/MinIO 与应用部署在同一台机器
  (本机 docker compose 或同 VPS),重跑上方脚本即可。
